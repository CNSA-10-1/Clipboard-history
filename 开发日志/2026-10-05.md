## 验证中抓到的两个问题

### 1. 只含一个文件夹的卡片，大小永远算不出来

统计原本只在"展开"时触发，而单条目卡片不会溢出、压根没有"展开"按钮。
修法：卡片渲染后延迟 300ms 也触发一次（延迟是为了让用户快速滚过去的卡片不白扫一遍磁盘）。

### 2. 剪贴板里有 .NET 序列化对象时，程序直接崩溃

```
System.PlatformNotSupportedException: BinaryFormatter ... have been removed
  at System.Windows.DataObject.OleConverter.ReadObjectFromHandle
  at ClipboardHistory.Services.ClipboardCapture.ReadBitmaps()
```

别的程序往剪贴板放二进制序列化对象时，WPF 会调 `BinaryFormatter` 去解，而 .NET 9 已经移除了它。
这个异常不是 `COMException`，重试封装接不住，一路穿过消息循环把进程带走。

**这不是多图的问题**——任何程序放一个序列化对象都能杀掉这个软件。加了三道防线：

1. `ClipboardRetry` 每个方法都加兜底的 `catch (Exception)`（非时序类错误放弃这条内容）
2. `App.OnClipboardChanged` 最外层再包一层 try/catch
3. 新增 `App.InstallCrashGuards()`：界面线程和后台线程的未处理异常都记日志、保住进程
4. 新增 `Services/Log.cs`：错误日志，带 512KB 上限（后台服务不能让它无限涨）

另外把 `ReadBitmaps` 里"读原始剪贴板对象"和"标准单图路径"拆开：
前者失败不再拖累后者，能拿到的图照样存下来。

**结论**：多张图片的**捕获**在 .NET 9 上实际不可达——Windows 剪贴板没有标准的"多图"格式，
而序列化数组又解不开。模型和卡片支持多张（手造数据验证过），但真实捕获永远只有 1 张。
这个限制已经写进代码注释和 `02-技术方案.md`。

# 第九轮（2026-10-06）

## S20 · 全量验收 ✅（抓到一个严重性能问题）

验收清单有 99 条，大部分在各自的步骤里已经验过。这轮重点跑**性能基准**和之前没覆盖的条目。

### 抓到并修掉：自定义 ScrollViewer 模板把虚拟化关掉了

性能一测就发现不对——**空数据 858ms / 105MB，500 条数据 4.6s / 176MB**，
成本随条目数线性增长，这是虚拟化没生效的典型特征。

先隔离出代价出在哪儿：**500 条数据加载完但窗口不显示时，内存只有 98.5MB**（和空数据一样）。
所以数据和加载都没问题，**70MB 和 3.8 秒全出在渲染列表上**。

做个对照实验，临时把列表的自定义滚动条样式去掉，用 WPF 默认的：

| | 自定义模板 | 默认模板 | 空数据 |
|---|---|---|---|
| 冷启动 | 4655 ms | **1198 ms** | 858 ms |
| 工作集 | 176.5 MB | **109.5 MB** | 105 MB |

**元凶确认**：模板里的 `ScrollContentPresenter` 漏了 `CanContentScroll` 的传递。
这个属性在 presenter 上默认是 false，而**没有逻辑滚动就没有虚拟化**——
500 张卡片被全部真实创建出来。系统的默认模板里有这句，自己写模板时极容易漏。

加上 `CanContentScroll="{TemplateBinding CanContentScroll}"` 后恢复正常，
并在模板里写了注释说明这句不能删。回归方法也写进了验收文档。

### 性能结果（Release，500 条数据）

| 指标 | 目标 | 实测 |
|---|---|---|
| 冷启动 | < 2 秒 | 1.2 秒 ✅ |
| 私有内存 | < 80 MB | 58.9 MB ✅ |
| 打开窗口 | < 300 ms | 26 ms ✅ |

顺带修正了指标定义：内存该看**私有内存**而不是工作集——工作集含 .NET 运行时和
WPF 程序集映射进来的共享页，那部分不是程序能控制的，拿它当指标会永远超标。

新增 `工具/测量性能.ps1`。写的时候踩了两个坑（都写进脚本注释了）：
轮询里不能用 `Get-Process | Where-Object { $_.Path ... }`（读每个进程的 Path 要打开句柄，
一轮几百毫秒，量到的是轮询本身），也不能用会抛异常的 `OpenExisting`。

## S21 · 打包 ✅（重启验证待用户）

新增 `build.bat`。比最简版多做三件事：先删残留的 `*_wpftmp.csproj`（否则报 MSB1011）、
检查程序是否在运行（否则 exe 被占用，MSB3021）、打包完再清一次临时工程。

产物：**单文件 `剪贴板历史.exe`，385 KB**（文档里原来估的 2MB 偏高，已修正）。

验证：双击能跑、单实例生效、exe 有图标、**开机自启写入的路径正确指向发布版 exe**。
测完把自启项关掉了——指向 `bin/Release/...` 这种构建产物目录不干净，
等用户把 exe 放到固定位置再开。

**剩下的只有一件事需要用户做**：把 exe 放到一个固定位置 → 设置里开自启 → 重启电脑确认。
这个我做不了（不能重启用户的机器）。

## 全程小结

S0–S21 共 22 步走完，阶段 1–7 全部结束。

开发过程中抓到并修掉的真问题（按严重程度）：

| 问题 | 后果 |
|---|---|
| 系统 MessageBox 按 Esc 取消后仍执行 | **丢数据**（清空历史撤不回来） |
| 改 JSON 命名策略导致旧存档读成 0 条 | **丢数据**（下次复制会用空列表覆盖存档） |
| 剪贴板里的 .NET 序列化对象 | **程序崩溃**（BinaryFormatter 在 .NET 9 已移除） |
| 自定义 ScrollViewer 模板关掉虚拟化 | 500 条时冷启动 4.7 秒、内存 176MB |
| 去重合并时丢下刚写的图片文件 | 磁盘垃圾（复制同一张图两次就会产生） |
| 单文件夹卡片的大小永远算不出 | 功能缺失 |
| 设置窗口 / 对话框跑到屏幕外 | 用户够不着 |
| `Checked` 事件处理器挂不上 | 文件夹大小算不出来 |
| 搜索筛选完全不生效且不报错 | 功能缺失 |

这些全都写进了对应的规范或验收清单，附了回归方法。
