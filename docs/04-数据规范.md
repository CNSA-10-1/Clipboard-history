# 数据规范

> 改数据结构或清理逻辑时读这份。**增删字段要同步更新本文件。**

## 数据放在哪

```
%AppData%\ClipboardHistory\
├─ index.json          # 所有条目的元数据
├─ index.json.bak      # 上一次的索引（原子写入时自动产生）
├─ settings.json       # 用户设置
└─ images\
   ├─ {imageId}.png        # 图片原图（仅截屏这类"真图片"有）
   └─ {imageId}_thumb.png  # 缩略图（长边 ≤ 200px，列表显示用这个）
```

**`{imageId}` 是每张图各自的 GUID，不是条目 id。**
因为一条记录可以带多张图（见 `ClipItem.Images`），用条目 id 命名的话第二张就覆盖第一张了。

**图片文件的缩略图也放这里**，用同一套 `{guid}_thumb.png` 命名，通过
`FileEntry.ThumbFile` 引用。**没有原图**——原图就是用户自己磁盘上那个文件，不复制一份进来。

路径通过 `Environment.GetFolderPath(SpecialFolder.ApplicationData)` 拼出来，不要写死 `C:\Users\...`。

设置窗口里有「打开数据文件夹」按钮，方便用户查看和备份。

## 数据模型

```csharp
public enum ClipKind { Text, Image, Files }

public sealed class FileEntry
{
    public string Path { get; set; } = "";
    public bool IsDirectory { get; set; }   // true = 文件夹，false = 文件
    public long SizeBytes { get; set; }     // 文件：写入时读 FileInfo.Length；文件夹：-1 表示"未统计"
    public string ThumbFile { get; set; } = ""; // 仅图片文件：缩略图文件名，其它情况空串
}

public sealed class ImageEntry
{
    public string ImageFile { get; set; } = ""; // 原图文件名
    public string ThumbFile { get; set; } = ""; // 缩略图文件名
    public int Width { get; set; }
    public int Height { get; set; }
    public long SizeBytes { get; set; }
}

public sealed class ClipItem
{
    public string Id { get; set; } = "";        // GUID，图片文件名也用它
    public ClipKind Kind { get; set; }
    public string Text { get; set; } = "";      // 文字内容；文件类型时存用于搜索的文件名拼接
    public FileEntry[] Files { get; set; } = [];// 仅 Kind == Files 时有值
    public ImageEntry[] Images { get; set; } = [];// 仅 Kind == Image 时有值（可能是多张）
    public string Hash { get; set; } = "";      // 内容指纹，去重用
    public DateTimeOffset CreatedAt { get; set; } // 最近一次复制时间，列表排序依据
    public bool Pinned { get; set; }
    public long SizeBytes { get; set; }         // 占用空间，容量淘汰用
}
```

### 字段说明

- **`Files` 里同时存文件和文件夹**，用 `IsDirectory` 区分。一次复制 3 个文件 + 1 个文件夹只产生**一张卡片**。
- **`IsDirectory` 必须在写入时确定并保存**。如果筛选时用 `File.Exists` 现算，文件被移动/删除后就判断不出来，卡片会从"文件"筛选里莫名消失。
- **`Text` 在文件类型下也要填**（把文件名用空格拼起来），这样搜索能搜到文件名。
- **`SizeBytes`**：文字按 UTF-8 字节数算；图片按原图文件大小算；文件按路径长度算（文件本体没有复制进来，所以按路径字符串大小计，可忽略），**再加上给图片文件生成的缩略图大小**——缩略图是实打实写在磁盘上的，不计进去容量上限就守不住了。
- **`FileEntry.IsImage`** 是**计算属性**，按扩展名判断（`.jpg` `.png` `.gif` 等十余种），不写进 `index.json`。
  只看扩展名、不碰磁盘：路径是复制那一刻存下来的，扩展名不会变；用 `File.Exists` 现算的话，
  文件被移动后判断结果会翻来覆去，卡片在「图片」筛选里忽有忽无（和 `IsDirectory` 同一个理由）。
- **`FileEntry.ThumbFile`** 会让界面收到变更通知。这个功能上线**之前**存的老记录是没有缩略图的，
  卡片显示出来之后会在后台补生成，补完靠这条通知把预览刷出来——不发通知界面会一直停在图标上。

### FileEntry.SizeBytes 为什么单独存

文件/文件夹卡片的**详情展开区要显示每个条目的大小**（见 [03-设计规范.md](03-设计规范.md)），
所以需要 `FileEntry` 自带大小，而不是只在外层 `ClipItem.SizeBytes` 上记一个总数。

- **文件**：写入时读一次 `FileInfo.Length` 存下来。之后文件被改大了也不会更新——这是历史记录，记的是"当时的样子"
- **文件夹**：写入时**不统计**（统计文件夹大小要递归遍历，可能几万个文件，会卡住剪贴板监听）。
  存 `-1` 表示"未统计"，用户**展开详情时**才在后台线程按需算，算完写回并更新界面。
  统计策略：最多遍历 5000 个文件或 2 秒，超了就停下来显示"较大"
- **文件已不存在**：显示"已失效"，大小显示"—"

## 枚举的序列化

`index.json` 里 `Kind` 要存成**字符串**（`"Text"` / `"Image"` / `"Files"`）而不是数字，方便人眼看和手工排查。

→ 用 `JsonStringEnumConverter`，写在 `JsonSerializerOptions.Converters` 里。

- `version` 是给以后改数据结构留的升级位。读到不认识的版本时，备份旧文件然后重建。
- 时间统一存**带时区的 ISO 8601**（`DateTimeOffset` 序列化后的格式），避免换时区后时间错乱。
- 字段名用**小驼峰**（`id` / `createdAt` / `items`）。

### 读索引时必须做的两道防线

毁掉用户的历史最快的方式，就是"没读懂 → 当成空的 → 用空列表覆盖写回去"。
所以读 `index.json` 时有两条硬性要求：

1. **反序列化要大小写不敏感**（`PropertyNameCaseInsensitive = true`）。
   严格匹配的话，任何一次字段改名都会让整个文件解析成 0 条，然后被空列表覆盖。
2. **解析出 `version <= 0` 就当成读不懂**，把原文件改名留档（`index.unreadable-<时间戳>.json`），
   再从空列表开始，**绝不覆盖**。

同样地，`version` 比当前支持的更新时也留档不读——硬读进来再保存会把新版本写入的字段悄悄抹掉。

## settings.json 格式

```json
{
  "version": 1,
  "retentionDays": 3,
  "maxTotalMB": 500,
  "autoStart": false,
  "theme": "System"
}
```

| 字段 | 类型 | 默认值 | 取值范围 | 说明 |
|---|---|---|---|---|
| `retentionDays` | int | `3` | 1–365 | 保留天数 |
| `maxTotalMB` | int | `500` | 50–10240 | 最大总容量（MB） |
| `autoStart` | bool | `false` | — | 开机自启 |
| `theme` | string | `"System"` | `Light` / `Dark` / `System` | 主题 |

**非法输入的处理**：读取时若值超出范围或类型不对，回退到默认值并记一条日志；设置界面输入非法时给提示并回退到**上一次的有效值**，绝不把坏值写进文件。

## 内容指纹（去重用）

| 类型 | 指纹算法 |
|---|---|
| 文字 | `SHA256(UTF8(text))` |
| 图片 | `SHA256(png 字节)` |
| 文件 | `SHA256(UTF8(按原顺序拼接的小写路径，用 \n 分隔))` |

**去重规则**：新增内容时先算指纹，在**全部**条目里找同指纹的（不只是相邻的）：

- 找到了 → 把那条的 `CreatedAt` 更新为现在，移到列表顶部，**不新增卡片**
- 没找到 → 新建条目

不同 `Kind` 之间不会指纹相同，天然互不干扰。

## 排序规则

列表按这个顺序排：

1. **置顶的排在最前**（`Pinned = true`）
2. 同组内按 `CreatedAt` **降序**（最新的在上）

置顶组内部也按 `CreatedAt` 降序。

## 清理规则

清理在两个时机触发：**应用启动时**、**每小时一次的定时器**，以及**用户改了保留天数/容量的设置后立刻**。

### 1. 过期清理

```
删除满足全部条件的条目：
  Pinned == false
  且 CreatedAt < 现在 - retentionDays 天
```

**置顶项永远不参与过期清理。**

### 2. 容量淘汰

```
计算所有条目 SizeBytes 之和
若总和 > maxTotalMB * 1024 * 1024：
    从「未置顶」的条目里挑 CreatedAt 最旧的删除
    重复，直到总和降到上限以下，或未置顶条目已删光
```

**如果未置顶的都删光了还是超限，就停下**（说明置顶内容本身就超了，这种情况不该再删用户明确要保留的东西）。不删置顶项。

### 3. 删除条目时要连带做的事

- 图片条目：删掉 `images\{id}.png` 和 `images\{id}_thumb.png`
- 图片文件条目：删掉它的 `FileEntry.ThumbFile`
  （⚠️ 去重合并时删的是**新写下的那份**，漏掉这里的话，"同一张照片复制两次"就会留下一张孤儿缩略图）
- 写完索引
- 删文件失败（被占用等）不要抛异常中断，记日志跳过即可——孤儿文件下次启动时统一清理一次

### 4. 数据文件夹自检

启动时跑一遍（见 `Services/DataMaintenance.cs`）：

| 清理项 | 判断依据 |
|---|---|
| 孤儿图片 | `images\` 里没有被**任何地方**引用的 **`.png`** → 删掉 |
| 残留的 `index.json.tmp` / `settings.json.tmp` | 上次写到一半崩溃留下的 → 删掉 |
| `index.unreadable-*.json` 留档 | 只保留最近 **3** 份，更早的删掉 |

**孤儿图片只删 `.png`**：这个目录本来就是我们放的 png，但用户万一往里丢了个别的东西，
不该被当成垃圾收走。

**"被引用"有两处，漏一处就会误删：**
`ClipItem.Images` 里的 `ImageFile` / `ThumbFile`，**以及** `ClipItem.Files` 里每个
`FileEntry.ThumbFile`。漏掉后者的话，下次启动会把用户**所有照片的预览图**当成孤儿删光，
而且完全无声——卡片还在，只是预览集体消失，用户根本不知道发生了什么。

**执行顺序：先删条目、再扫文件夹。** 删条目时图片文件可能被别的程序占用删不掉，
那次失败留下的孤儿正好在紧接着的扫描里被收走。反过来的话，这一轮新产生的孤儿
要等到下一个小时才会被清理。

### 5. 清空全部历史

删掉 `index.json` 里的所有条目 + `images\` 下所有文件，`settings.json` **不动**（设置保留）。需要用户二次确认。

## 原子写入

`index.json` 不能直接覆盖写——写一半崩溃会让整个历史丢失。

```
1. 序列化到 index.json.tmp
2. 若 index.json 已存在 → File.Replace(tmp, index.json, index.json.bak)
   否则 → File.Move(tmp, index.json)
3. 异常时删除 tmp，保留原文件不动
```

写入加锁（`SemaphoreSlim`），因为剪贴板事件和 UI 操作可能同时触发写入。
